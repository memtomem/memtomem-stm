# memtomem-stm Implementation Review — full source sweep

Date: 2026-06-10
Scope: Full `src/memtomem_stm/` tree (~22k LOC) across 12 modules: daemon stack, `mms hook`/daemon CLI, proxy manager pipeline, compression tiers, MCP server + tracing, surfacing engine, surfacing I/O (incl. the #398 network transport), proxy CLI, host/project/drift state, config + privacy, persistence/shared-state primitives, and supporting proxy stages.

Method: 12 parallel module reviewers (each reading its files in full + the covering tests) → adversarial refute-by-default verification of every finding (a second independent skeptic re-attacked each critical/high) → the suggested fix was separately adjudicated for regressions → synthesis. Empirical reproductions were run against this checkout's venv (anyio 4.13.0, mcp 1.27.0) for the cancel-scope and httpx-MRO findings.

Result: 71 findings raised, **64 adversarially confirmed** (3 high, 17 medium, 44 low), 9 rejected by verification. Known-deferred items (FieldExtract indent router, #288 inert index, metrics read-lock, surfacing falsy-checks, etc.) were excluded from scope up front.

## Overall assessment

The codebase is mature and the recent fix wave (#384–#410) closed the compression monotone-tier family and most surfacing gaps cleanly — those shipped invariants held up under re-attack and were not re-litigated. The net-new value of this sweep is three **structural seams the fix wave did not reach**:

1. **The cache layer is blind to progressive delivery and durable demotion.** It persists a progressive *first chunk* whose `read_more` key expires (H1, silent tail-data-loss), and it re-serves cached results without re-applying feedback demotion (M7, #39). The cache is treated as opaque-text storage while the pipeline now produces stateful, keyed responses.
2. **The brand-new network LTM transport (#398) is under-hardened.** Its httpx error class is not in the reconnect tuple (H3 — surfacing dies permanently after the first network blip), its paths are untested by the reconnect suite (M/#11), and URL userinfo credentials can be logged (#41).
3. **Config propagation and env handling are fragile.** Enabling the proxy via env silently drops the entire JSON config (M1), `consumer_model` never reaches surfacing (M2), and a single malformed env var collapses the whole file config to defaults (#57).

The `#410` cancel-scope fix is also incomplete in two ways: it misses the `ExceptionGroup`-wrapped shape that anyio actually raises (H2) and does not cover the daemon teardown path at all (#4, #21). Daemon robustness (newest stack, least-reviewed) and a long tail of validation/edge cases make up the rest.

## Findings by module

### Proxy pipeline / cache / progressive (`proxy/manager.py`)

- **[high / fix-ok]** Progressive first-chunk is cached, so cache hits hand the agent a read_more key that has already expired
  - `src/memtomem_stm/proxy/manager.py:1999` (bug)
  - what: After the PROGRESSIVE branch (L1551-1559) or the progressive_fallback tier (L1666-1695) runs, `compressed` is the *first chunk* whose footer embeds `stm_proxy_read_more(key="<uuid>", offset=...)` pointing at a freshly created progressive-store entry with a TTL. The cache store at L1999 unconditionally persists `compressed` (no progressive guard; only `not non_text_content` gates it, and progressive responses are text-only). On a later cache hit, `_on_cache_hit` (L1103-1127) returns the stored first chunk verbatim without re-materializing the progressive entry. By then the original store entry has been evicted (TTL / max_stored), so the agent follows the cached footer's `stm_proxy_read_more(key=...)` and gets `"Progressive delivery key '<key>' not found or expired."` (read_more L1057-1058). The truncated tail is permanently unreachable on every cached read — a silent data-loss path for any tool configured with PROGRESSIVE or any large response that triggers the progressive ratio-fallback.
  - fix: Track whether the response went through a progressive path (the code already computes `progressive_fallback`, and the primary branch is gated on `tc.compression == PROGRESSIVE`). Skip `cache.set` when the returned `compressed` is a progressive first-chunk (e.g. `if self._cache is not None and not non_text_content and not _is_progressive_response:`), or cache the full pre-progressive `cleaned` text and re-run progressive delivery on hit. Add a regression test asserting progressive responses are not stored in the cache.
- **[medium / fix-ok]** No test pins that progressive responses are excluded from the cache (the missing invariant behind the stale-key bug)
  - `tests/test_proxy_manager_pipeline.py:1` (test-gap)
  - what: The cache layer and the progressive layer are individually tested, but there is no test asserting the cross-cutting invariant 'a response delivered via the progressive path is not stored in the cache' (or, if stored, is re-materialized on hit). That gap is precisely why the high-severity stale-read_more-key bug (manager.py L1999) is latent. The progressive F6 tests at L479-635 only exercise `_apply_surfacing_on_progressive` in isolation; none drive `_call_tool_inner` end-to-end with a cache configured and a progressive/progressive-fallback response, then a second identical call, asserting the second call does not return a dead read_more key.
  - fix: Add an integration test: configure PROGRESSIVE (or force a ratio violation), call the tool with a cache, assert the cache was not populated with the first-chunk (or that a second call yields a live read_more key). This both fixes the documentation gap and locks the fix for the L1999 bug.
- **[low / fix-ok]** register_proxy_tool sets .parameters/.fn_metadata outside the version-drift guard, so a field rename aborts the whole tool-registration loop
  - `src/memtomem_stm/proxy/_fastmcp_compat.py:108` (error-handling)
  - what: The module deliberately wraps fastmcp-internal access in try/except: `server.add_tool` (L79-94) and `_tool_manager._tools.get` (L95-105) both degrade with a WARNING when 'FastMCP API may have changed'. But the subsequent mutations `registered.parameters = info.input_schema` (L108) and `registered.fn_metadata = _PASSTHROUGH_METADATA` (L109) are *outside* any try/except. On a future fastmcp that renames or removes these pydantic fields, assignment raises (pydantic v2 rejects setattr to a non-field), and since the caller in server.py L250-255 loops `register_proxy_tool` with no per-tool guard, one renamed field aborts registration of every remaining proxied tool and fails server startup — the exact silent-degradation the rest of this module is built to avoid. The module-level `_PASSTHROUGH_METADATA = FuncMetadata(arg_model=..., output_schema=..., output_model=..., wrap_output=...)` (L33-38) has the same unguarded version-drift exposure at import time.
  - fix: Wrap the `.parameters`/`.fn_metadata` assignment in the same try/except + WARNING pattern used for `add_tool` and `_tools.get`, so a fastmcp field rename downgrades to 'tool registered with default schema' rather than crashing the registration loop. Add a unit test for register_proxy_tool (currently only `_tag_annotations_title` is tested).
- **[low / fix-ok]** stop() closes the extractor but does not null it, so a stop->start cycle reuses a closed httpx client and AssertionErrors
  - `src/memtomem_stm/proxy/manager.py:421` (bug)
  - what: `stop()` closes `self._extractor` but leaves the attribute pointing at the now-closed instance, unlike `self._llm_compressor` two lines above which is set to `None` (L419). `start()` does not reset `_extractor` either. On a stop->start lifecycle (start() explicitly supports double-start, and reconnect/restart flows exercise it), `_get_extractor()` checks `if self._extractor is None` (L936) — finds it non-None — and returns the closed extractor. `FactExtractor.extract()` then hits `assert self._client is not None` (extraction.py L255/266/296/328) because `close()` set `_client = None` (extraction.py L351-354), raising AssertionError on the first post-restart extraction. The same asymmetry means a restarted manager never rebuilds the extractor.
  - fix: Set `self._extractor = None` after `await self._extractor.close()` in `stop()`, mirroring the `_llm_compressor` cleanup. Add a lifecycle test that calls stop() then triggers extraction and asserts a fresh extractor is built (the existing `test_stop_closes_extractor` only checks close() was awaited).
- **[low / fix-ok]** context_query type guard exists on the cache-hit path but is missing on the main miss path
  - `src/memtomem_stm/proxy/manager.py:1272` (bug)
  - what: `_on_cache_hit` defensively coerces a non-str `_context_query` to None before forwarding to surfacing: `context_query if isinstance(context_query, str) else None` (L1126). The main miss path in `_call_tool_inner` does `context_query = arguments.get("_context_query")` (L1272) with no type guard and threads the raw value into `_apply_compression`, `_apply_surfacing`, `_apply_surfacing_on_progressive`, `_auto_index_response`, and `_extract_and_store`. An agent passing `_context_query` as a JSON object/number (it is plumbed through MCP arguments) reaches scorers/compressors as a non-str on the miss path but is sanitized on the hit path — an inconsistency that can surface as a TypeError inside a scorer for the same input depending only on cache state.
  - fix: Apply the same `isinstance(context_query, str)` guard in `_call_tool_inner` immediately after extracting it (e.g. `cq = arguments.get("_context_query"); context_query = cq if isinstance(cq, str) else None`), so both paths sanitize identically. Add a test passing a non-str `_context_query` through `call_tool`.

### MCP server lifecycle & tracing (`server.py`, `observability/`)

- **[high / fix-ok]** #410 AnyIO cancel-scope handler misses ExceptionGroup-wrapped errors (the real production shape)
  - `src/memtomem_stm/server.py:1443` (error-handling)
  - what: main() catches the AnyIO cancel-scope shutdown error with `except RuntimeError as e: if _is_anyio_cancel_scope_shutdown_error(e): ... return`. But mcp's `_mcp_server.run()` runs inside `async with anyio.create_task_group()` (mcp/server/lowlevel/server.py:673) under `anyio.run()`. In anyio 4.13 (the pinned version), any exception escaping a task group is wrapped in a `BaseExceptionGroup`/`ExceptionGroup`, which is NOT a `RuntimeError`. I reproduced this empirically against the repo venv: both a directly-raised RuntimeError and a spawned-task RuntimeError surface from `anyio.run()` as `ExceptionGroup` (IS_RUNTIMEERROR: False). When the cancel-scope error escapes through the task-group boundary on stdio EOF, this guard is skipped, the error falls through to the generic `except Exception` barrier, gets logged at ERROR (`logger.exception("STM MCP server terminated with an unhandled exception")`) and re-raised — defeating the entire purpose of #410 (clean shutdown becomes a noisy crash + non-zero exit). The #410 test passes only because it injects a *bare* RuntimeError as `mcp.run`'s side_effect, bypassing the real anyio task-group wrapping; the ExceptionGroup-wrapped variant is untested.
  - fix: Walk ExceptionGroups before classifying. Add a helper that, for a `BaseExceptionGroup`, checks `exc.exceptions` recursively (or uses `eg.split(RuntimeError)`) for any leaf matching `_is_anyio_cancel_scope_shutdown_error`, and treat the group as clean only if ALL leaves are cancel-scope-shutdown errors (re-raise the rest). Update the test to inject an `ExceptionGroup("...", [RuntimeError(<cancel-scope msg>)])` so the real shape is pinned, not just the bare RuntimeError.
- **[low / fix-incomplete]** traced() can break the proxy hot path when the Langfuse client method raises
  - `src/memtomem_stm/observability/tracing.py:73` (error-handling)
  - what: The module docstring states tracing functions 'gracefully return None/nullcontext' and proxy/manager.py:1142 documents that tracing must not break the proxy path. But `traced()` calls `client.start_as_current_observation(name=name, **kwargs)` with no guard. This is used as `with traced(...): <await upstream proxy call>` across the proxy hot path (manager.py:1059, 1119, 1156, 1530, 1607, 1789, 1808) and surfacing (engine.py:359, 441). If the live Langfuse SDK raises during `__enter__` (OTEL context corruption, SDK internal error, misconfigured exporter) the exception propagates and fails the entire proxy/surfacing call — exactly the failure mode the invariant forbids. The graceful-degradation guarantee only holds for `client is None` / sampled-out, not for a client whose method raises. No test pins the client-method-raises case (grep for `start_as_current_observation.*side_effect`/`raise` in tests/ returns nothing).
  - fix: Wrap the client call: `try: return client.start_as_current_observation(name=name, **kwargs) except Exception: logger.debug("Langfuse traced() failed, falling back to nullcontext", exc_info=True); return nullcontext()`. Add a test that sets a client whose `start_as_current_observation` raises and asserts `traced()` still returns a usable context manager (proxy path unaffected).
- **[low / fix-ok]** Surfacing configured-enabled but proxy-disabled is silently skipped with no startup log
  - `src/memtomem_stm/server.py:156` (docs-drift)
  - what: The surfacing-engine init block (line 156, `if config.surfacing.enabled:`) is nested inside `if config.proxy.enabled:` (line 104). So with `proxy.enabled=false` (the default control-only mode) but `surfacing.enabled=true` in the JSON config, surfacing is silently disabled at startup. The only log emitted is `"Proxy disabled (enabled=false) — only STM control tools available"` (line 226), which says nothing about surfacing being configured-on-but-skipped — a config-says-enabled / runtime-no-op mismatch with no dedicated log line. This parallels the documented #288 `auto_index` 'inert' warning pattern, but surfacing has no equivalent inert warning. It is observable on demand via `stm_proxy_health` (`_surfacing_bootstrap_lines` emits 'inactive (proxy disabled)' at line 620), which keeps this low, but an operator reading only startup logs would not see it.
  - fix: When `not config.proxy.enabled and config.surfacing.enabled`, extend the line-226 log (or add a sibling warning) noting that surfacing is configured-enabled but inactive because the proxy is disabled — mirroring the #288 'inert' warning so config/runtime mismatches are visible at startup, not only via the health tool.
- **[low / fix-ok]** No test pins that proxied tools advertise BEFORE STM utility tools end-to-end through real FastMCP
  - `src/memtomem_stm/server.py:259` (test-gap)
  - what: `_move_stm_tools_to_end` reaches into the private `server._tool_manager._tools` insertion-ordered dict (line 392) to satisfy #228 (proxied tools first). The unit tests in TestAdvertiseOrder validate the helper against a hand-built SimpleNamespace stand-in (`_make_server`), and the end-to-end TestAdvertiseObservabilityFlag tests only assert the *membership* of registered tools, never their *order* through a real FastMCP `list_tools()`. So a FastMCP upgrade that changes `_tool_manager._tools` from an insertion-ordered dict to something else (or where `list_tools()` re-sorts) would pass every existing test while silently regressing the #228 advertise order — the helper's degrade-to-warning path (line 393) only fires on AttributeError, not on a semantic change to iteration order. The invariant the helper exists to protect has no integration pin.
  - fix: Add an integration test that registers two fake proxied tools on the real `mcp` FastMCP instance, calls `_move_stm_tools_to_end(mcp)`, then asserts `[t.name for t in mcp._tool_manager.list_tools()]` places every proxied (`__`-containing) name ahead of every `stm_*` utility name — pinning the order against the live FastMCP API, not a stand-in.

### LTM client & feedback persistence (`surfacing/mcp_client.py`, `feedback*`)

- **[high / fix-incomplete]** Network LTM transports (#398) don't catch httpx errors in _TRANSPORT_ERRORS — no reconnect, surfacing stays down until restart
  - `src/memtomem_stm/surfacing/mcp_client.py:339` (error-handling)
  - what: #398 added `sse` and `streamable_http` LTM transports, but `_TRANSPORT_ERRORS = (OSError, ConnectionError, EOFError, BrokenPipeError, asyncio.TimeoutError)` only covers the stdio failure modes. The mcp network clients (`sse_client` / `streamablehttp_client`) propagate `httpx` errors — `httpx.ConnectError`, `httpx.ReadTimeout`, `httpx.RemoteProtocolError`, `httpx.ConnectTimeout` — whose MRO is `httpx.* -> TransportError -> RequestError -> HTTPError -> Exception`, with NO `OSError`/`ConnectionError`/`asyncio.TimeoutError` ancestor (verified via `uv run python`). So a transient network drop on the brand-new transports falls through `except self._TRANSPORT_ERRORS` straight into the generic `except Exception` at search:473, which returns outcome `"call_error"` and never calls `_reconnect()` and never sets `_needs_reconnect`. The session is then a dead `ClientSession` for the rest of the process lifetime — surfacing is permanently off over the network path after the first blip, with no self-healing. stdio works only because pipe failures ARE `OSError`/`BrokenPipeError`.
  - fix: Add the httpx transport error base to `_TRANSPORT_ERRORS` when network transports are configured (e.g. import `httpx` lazily and include `httpx.TransportError`, or at minimum `httpx.HTTPError`), guarded so the import is optional. Add a reconnect test that injects an `httpx.ConnectError`/`httpx.ReadTimeout` against an `sse`/`streamable_http` adapter — the existing reconnect suite only injects `ConnectionError` against the default stdio config.
- **[medium / fix-ok]** Demotion filter is bypassed on the cache-hit path — only _invalidated_ids (in-process) gates cached results, not durable demotion
  - `src/memtomem_stm/surfacing/engine.py:572` (bug)
  - what: #404 applies `_feedback_demoted_ids` only on the cache-MISS path (around engine.py:758-793). `_render_cached` filters cached results solely against `_invalidated_ids` (engine.py:572-576) — an in-memory set populated only by feedback submitted through *this* engine's `handle_feedback` during the cache TTL. A memory that crosses the durable demotion threshold via feedback recorded in a *different* process (the proxy and daemon share `stm_feedback.db`) is NOT filtered from a warm cache entry in this process: cache hits keep re-surfacing it until the entry TTL-expires. The #404 comment claims demotion sits before cache write "so a rejected memory does not keep reappearing from a cached query after process restart" — true across restarts, but within a live process the cache hit path silently re-surfaces durably-demoted memories. Bounded by `cache_ttl_seconds` (default 60s) and the daemon disables the cache, which keeps this medium rather than high.
  - fix: Also intersect the cached list with `self._feedback_demoted_ids([str(r.chunk.id) for r in cached])` in `_render_cached` (gated on `_record_feedback_events` + `feedback_demotion_enabled`, mirroring the miss path), or document explicitly that demotion is miss-only and bounded by cache TTL.
- **[medium / fix-incomplete]** Reconnect/retry test coverage does not exercise the network transport paths added by #398
  - `tests/test_mcp_client_reconnect.py:49` (test-gap)
  - what: `TestLtmTransportSelection` only asserts `_open_transport()` returns the right client object for `sse`/`streamable_http`; it never drives `search()`, `_reconnect()`, error classification, or version negotiation over a network transport. Every reconnect-retry, cancellation, lazy-start, and None-content test constructs `McpClientSearchAdapter(SurfacingConfig())` — i.e. the default `stdio` transport — and injects `ConnectionError`/`OSError`, which happen to be in `_TRANSPORT_ERRORS`. The consequence is that the `_TRANSPORT_ERRORS`-mismatch bug above (httpx errors not classified as transport errors on the network path) ships completely unpinned: there is no test that would fail when the new transports mis-handle a transient network error. This is the load-bearing invariant (reconnect/heal on transient transport failure) that the network path the PR shipped has zero coverage for.
  - fix: Parametrize the reconnect/heal suite over `ltm_mcp_transport in {stdio, sse, streamable_http}` (with `ltm_mcp_url` set) and inject the transport-appropriate exception types, asserting `_reconnect` fires and outcome is `transport_error` for httpx network errors.
- **[low / fix-incomplete]** LTM endpoint URL logged at INFO can leak credentials embedded in the URL userinfo
  - `src/memtomem_stm/surfacing/mcp_client.py:299` (security)
  - what: `_target_display()` returns `self._config.ltm_mcp_url` verbatim for network transports, and it is logged at INFO in `start()` (line 262-266) and `_reconnect()` (line 343-347). Auth headers are correctly kept out of logs, but a `streamable_http`/`sse` URL of the form `https://user:token@host/mcp` (RFC-3986 userinfo) would write the embedded credential to the proxy log on every connect and reconnect. The new network transport makes credential-in-URL a realistic configuration that did not exist on the stdio path.
  - fix: Redact userinfo before logging the URL (e.g. `urlsplit`, blank out `username`/`password`, `urlunsplit`) in `_target_display()` for network transports.

### Surfacing engine & demotion (`surfacing/engine.py`)

- **[medium / fix-ok]** no_results_demoted skip label (#404) is unclassified — silently dropped from stm_surfacing_stats output
  - `src/memtomem_stm/surfacing/engine.py:793` (bug)
  - what: PR #404 added a new operator-facing skip reason `"no_results_demoted"` recorded at engine.py:793 to distinguish "score filter passed but feedback-demotion killed everything" from `no_results_dedup`/`no_results_score`. But the label was NOT added to (a) the `SkipReason` Literal in observability.py (lines 32-60), nor (b) `HEALTHY_SKIP_REASONS`, nor (c) `FAULT_SKIP_REASONS` (lines 77-101). The stm_surfacing_stats consumer `_split_skip_reasons_by_category` (server.py:1039-1040) renders ONLY reasons present in one of those two frozensets and "silently drops" anything else (its own docstring at server.py:1029 admits this, relying on the exhaustiveness test to catch gaps). I verified at runtime: a snapshot `{'no_results_demoted': 7, ...}` yields healthy_view/fault_view that both exclude it, dropped set = {'no_results_demoted'}.   - fix: Add `"no_results_demoted"` to the `SkipReason` Literal (observability.py:42-45 family) AND to `HEALTHY_SKIP_REASONS` (it is an expected threshold/no-results outcome, not a fault). Adding it to the Literal also makes `test_categorization_is_exhaustive_and_disjoint` enforce that it lives in exactly one set, restoring the CI guard the docstring promises.
- **[medium / fix-incomplete]** No test pins that no_results_demoted survives the healthy/fault split in stm_surfacing_stats
  - `tests/test_surfacing_engine.py:833` (test-gap)
  - what: The #404 demotion tests (`TestFeedbackDemotion`, engine test L833-934) only assert memory content presence/absence in the injected block — none assert the `no_results_demoted` observability counter is recorded, and none assert it reaches the rendered stats output through `_split_skip_reasons_by_category`. The absence of an equivalent for demotion is exactly why the previous finding shipped undetected: the categorization-exhaustiveness test inspects only `get_args(SkipReason)`, so a label added as a bare string in engine.py with no Literal member and no render-path test is invisible to CI.
  - fix: Add a test that drives the all-demoted path with a `SurfacingObservability` wired and asserts `snapshot()["skip_reasons"][tool] == {"no_results_demoted": 1}`, plus a render-path assertion that the label appears under the Healthy skips subsection of stm_surfacing_stats output (mirroring test_no_results_dedup_records_skip).
- **[low / fix-ok]** handle_feedback boost cap-prune is duplicated verbatim across single and batched paths
  - `src/memtomem_stm/surfacing/engine.py:368` (simplification)
  - what: The `_boosted_event_ids` overflow-prune block (compute excess, slice-delete oldest half) is copy-pasted identically in `handle_feedback` (L368-371) and `handle_feedback_batch` (L449-452). The same FIFO-prune shape also appears in `_claim_surfaced_ids` (L540-543) and `_invalidate_cache_for_feedback` (L504-507) — four sites of the exact `if len(d) > d_max: excess = len(d) - d_max//2; for k in list(d)[:excess]: del d[k]` idiom. This crosses the project's documented "extract a helper when a defensive pattern recurs 4+ sites" threshold (feedback_helper_extract_threshold). A single `_fifo_prune(mapping, cap)` helper would remove the duplication and the risk of one site drifting (e.g. a future cap change applied to three of four).
  - fix: Extract a module-level `def _fifo_prune(d: dict, cap: int) -> None:` and call it from all four sites; tests `test_boosted_event_ids_fifo_cap_evicts_oldest`, `test_invalidated_ids_fifo_cap_evicts_oldest`, and `test_prunes_to_cap` already pin the behavior so the refactor is safe.
- **[low / fix-ok]** Cache-hit path does not re-apply feedback demotion — a memory that crosses the durable demotion threshold mid-TTL can still resurface from cache
  - `src/memtomem_stm/surfacing/engine.py:545` (bug)
  - what: `_do_surface_miss` applies `_feedback_demoted_ids` BEFORE writing the cache (L766-785), so a NEW cache entry never contains a memory already over the negative-feedback threshold. But `_render_cached` (L545-628) filters cache hits only against the session-scoped `_invalidated_ids`, never against `_feedback_demoted_ids`. The miss-path comment at L763 claims demotion "sits before cache write so a rejected memory does not keep reappearing from a cached query after process restart" — that holds only at write time. Concrete gap: query Q caches [memA] while memA's durable negative count is 2 (threshold 3). A different session (or batched negatives) pushes memA's persisted count to 3. Within this process's cache TTL window (default 60s), repeating Q is a cache HIT and re-injects memA, even though a fresh miss would now demote it. Within-session feedback partially masks this because `not_relevant`/`already_known` also populate `_invalidated_ids` (filtered on the hit path), so the window is narrow (cross-session threshold crossing during a live cache entry). Low severity given the 60s default TTL and the partial `_invalidated_ids` cover.
  - fix: Either apply `self._feedback_demoted_ids([str(r.chunk.id) for r in cached])` in `_render_cached` symmetric with the miss path, or scope the comment at L761-764 to clarify demotion is enforced at cache-write time only and document the TTL-bounded staleness. Given the cheap DB lookup is already gated behind `_record_feedback_events`/`feedback_demotion_enabled`, re-applying on the hit path is the consistent choice.

### Compression tiers (`proxy/compression.py`)

- **[medium / fix-ok]** LLM_SUMMARY success path returns model output verbatim with no max_chars enforcement
